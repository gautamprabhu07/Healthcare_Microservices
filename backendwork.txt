 Goal: turn the current course-style backend into a complete, resume-worthy,
 localhost-only backend that is ready for a frontend to be built on top of it.

 How to use this file
 --------------------

 PART A: AUDIT OF THE CURRENT REPOSITORY
=============================================================================

A1. What exists today
---------------------
 Service            Port(s)        What it actually does
 -----------------  -------------  -----------------------------------------
 api-gateway        4004           Spring Cloud Gateway. Routes /auth/** to
                                   auth-service and /api/patients/** to
                                   patient-service. A custom JwtValidation
                                   filter calls auth-service /validate on
                                   every patient request.
 auth-service       4005           Login (POST /login) returns a JWT.
                                   GET /validate checks a token. One seeded
                                   user (testuser@test.com / password123,
                                   role ADMIN). Postgres.
 patient-service    4000           Patient CRUD (list, create, update,
                                   delete). On create, calls billing over
                                   gRPC and publishes a PATIENT_CREATED
                                   Kafka event. Postgres. Swagger UI.
 billing-service    4001 / 9001    gRPC server with ONE method,
                                   CreateBillingAccount. It is a STUB: it
                                   logs the request and always returns
                                   accountId "12345". No database.
 analytics-service  (8080, bug)    Kafka consumer that LOGS patient events.
                                   Nothing is stored or exposed.
 infrastructure     -              AWS CDK stack (VPC, ECS, RDS, MSK) for
                                   LocalStack. Not needed for localhost.
 integration-tests  -              2 RestAssured test classes against the
                                   gateway.
 docker-compose.yml -              Runs everything locally (added by us).

A2. What works well (keep it)
-----------------------------
 - Clean microservice split with a database per service.
 - Three communication styles already shown: REST, gRPC and Kafka with
   Protobuf. This is the project's strongest resume point.
 - The gateway is the single entry point with centralised JWT validation.
 - Validation groups on the patient DTO (create and update use different
   rules).
 - Every service has a multi-stage Dockerfile.
 - Swagger/OpenAPI via springdoc in patient-service and auth-service.

A3. Bugs found (things that are wrong right now)
------------------------------------------------
 B1  analytics-service has no server.port. It listens on 8080 while
     docker-compose maps 4002, so port 4002 goes nowhere.
 B2  api-gateway application-prod.yml has a malformed URI:
     "http:/host.docker.internal:4005" (one slash is missing).
 B3  AuthController.login has no @Valid, so the validation annotations on
     LoginRequestDTO are ignored. An empty body reaches the service layer.
 B4  PatientNotFoundException returns 400. It should return 404.
     A duplicate email returns 400. It should return 409 (Conflict).
 B5  DELETE /patients/{id} returns 204 even when the patient does not
     exist. Nothing is checked.
 B6  The EmailAlreadyExistsException message is missing a space:
     "...already exists" + email gives "...already existsjohn@x.com".
 B7  PatientIntegrationTest asserts body("patients", notNullValue()), but
     the endpoint returns a JSON ARRAY with no "patients" field. The test
     can never pass.
 B8  The sample .http files point at an old LocalStack load-balancer host
     (lb-7e648e08.elb.localhost.localstack.cloud). Two of them bypass the
     gateway (localhost:4000) and send no token.
 B9  Patient create is not transactional. If billing (gRPC) fails after
     the patient row is saved, the client gets a 500 but the patient
     still exists without a billing account. The gRPC call also has no
     deadline, so a hung billing service hangs the request.
 B10 patient-service accidentally starts its own gRPC SERVER on port 9090,
     because grpc-spring-boot-starter brings both client and server. It
     serves nothing useful today (Step 8 gives it a real purpose).
 B11 Spring Security in auth-service auto-creates an in-memory user and
     prints "Using generated security password..." on startup. This is
     harmless noise that looks unprofessional.

A4. Shortcomings and missing features
-------------------------------------
 Security and auth
 - No way to create users (no register endpoint and no user management).
 - Roles exist in the JWT ("ADMIN") but nothing enforces them. Any valid
   token can do anything, including deleting patients.
 - Downstream services do not know WHO is calling. The gateway does not
   forward user identity.
 - No CORS configuration. A browser frontend on another port is blocked.
 - Every internal service port (4000, 4001, 4005 and others) is published
   to the host, so anyone can skip the gateway and its JWT check entirely.
 - The JWT secret is hardcoded in infrastructure/LocalStack.java, a
   committed file.
 - 401 responses from the gateway have an empty body.

 Patient domain
 - No GET /patients/{id}.
 - No pagination, search or sorting on the list. This does not scale and
   a frontend table needs it.
 - registeredDate is stored but never returned.
 - Minimal patient data: no phone or gender.
 - Only PATIENT_CREATED is published. Update and delete emit no events,
   so other services cannot react.

 Billing domain
 - Entirely fake (hardcoded account ID). No database, no invoices,
   no REST API.

 Analytics domain
 - Only logs. No storage and no API, so a dashboard has no data source.

 Healthcare features
 - No appointments or doctors, which are the core of any clinic system.
   This is the biggest functional gap for a "healthcare platform".

 Engineering quality
 - Schema is managed by ddl-auto=update plus data.sql. There are no
   versioned migrations (Flyway).
 - Error responses differ between services (a Map, an empty body, or the
   Spring default page). A frontend needs ONE predictable error shape.
 - No health checks (Spring Boot Actuator). docker-compose depends_on only
   waits for a container to START, not to be READY.
 - .proto files are copy-pasted into each service (billing_service.proto
   x2, patient_event.proto x2). They can silently drift apart.
 - No request or correlation IDs, so one request cannot be traced
   across services in the logs.
 - Tests: only empty contextLoads() tests and 3 integration tests (one of
   them broken). No unit tests at all.
 - docker-compose.yml is in .gitignore, so the way to run the project is
   not version-controlled.
 - No single API documentation entry point. Swagger is per service, and
   billing and analytics have none.

 PART B: TARGET ARCHITECTURE AND CONVENTIONS
=============================================================================
 Every step must follow these conventions. Prompts refer back to this part.

B0. Original plan vs. target architecture
-----------------------------------------
 The original plan (course diagram):
   Frontend -> API Gateway -> Auth, Patient, Analytics
   Patient --gRPC--> Billing
   Patient --Kafka "patient" topic--> Analytics, Notification
 In the repo today, Notification Service does not exist at all, Billing is
 a stub and Analytics only logs.

 What changes in the target, and why:
   + Appointment Service (new). The core healthcare workflow. It uses gRPC
     (patient lookup) and REST (doctor lookup) for service-to-service
     calls.
   + Notification Service (from the original plan, now actually built).
     Sends emails to a local Mailpit inbox you can open in the browser.
   + Billing becomes a real service. It is still created over gRPC, but it
     also consumes events and publishes its own.
   + Three Kafka topics instead of one (patient, appointment, billing).
     This gives a true event-driven system rather than a single
     notification pipe.
   + Analytics builds a read model from all topics and serves the
     dashboard.
   + The gateway becomes the ONLY entry point (service ports closed),
     with CORS, identity headers and one Swagger UI.
   + Every service with state gets its own Postgres (database-per-service).

 Target architecture:

   localhost:5173       |  + unified Swagger UI |  headers, X-Request-Id

B3. Roles and permissions
-------------------------
 Three roles: ADMIN, DOCTOR, RECEPTIONIST.

 Action                              ADMIN   RECEPTIONIST   DOCTOR
 ----------------------------------  -----   ------------   ------------------
 Manage users                        yes     -              -
 List doctors                        yes     yes            yes
 View patients                       yes     yes            yes
 Create / update patients            yes     yes            -
 Delete patients                     yes     -              -
 Book / reschedule / cancel appts    yes     yes            -
 View appointments                   yes     yes            own only
 Mark appointment COMPLETED/NO_SHOW  yes     -              own only
 View notification log / resend      yes     -              -
 View billing / invoices             yes     yes            -
 Create / pay / cancel invoices      yes     yes            -
 Analytics                           yes     -              -

 How it is enforced:
 - The gateway validates the JWT (through auth-service), REMOVES any
   X-User-* headers sent by the client (anti-spoofing), then adds
   X-User-Id, X-User-Email and X-User-Role from the token claims.
 - Each downstream service reads those headers with a small shared
   pattern (an interceptor or @RequiredRole annotation) and returns 403
   when the role is not allowed.

B4. Standard error response (every service, every error)
--------------------------------------------------------
 {
   "timestamp": "2026-10-02T10:15:30Z",
   "status": 404,
   "error": "Not Found",
   "message": "Patient not found with id 123...",
   "path": "/patients/123...",
   "fieldErrors": { "email": "Email should be valid" }   // only on 400
 }
 Status codes: 400 validation, 401 unauthenticated, 403 wrong role,
 404 not found, 409 conflict (duplicates or double-booking),
 422 invalid state change (for example paying a cancelled invoice),
 503 a downstream service is unavailable.

B5. Kafka topics and events (Protobuf)
--------------------------------------
 Topic          Events                                         Key
 -------------  ---------------------------------------------  -----------
 patient        PATIENT_CREATED, PATIENT_UPDATED,              patientId
                PATIENT_DELETED
 appointment    APPOINTMENT_BOOKED, APPOINTMENT_RESCHEDULED,   appointmentId
                APPOINTMENT_COMPLETED, APPOINTMENT_CANCELLED,
                APPOINTMENT_NO_SHOW
 billing        INVOICE_CREATED, INVOICE_PAID,                 invoiceId
                INVOICE_CANCELLED
 Every event carries: eventId (UUID), eventType, occurredAt (ISO-8601),
 plus its payload fields.

B6. Event-driven flows when finished
------------------------------------
 1. Patient created -> (gRPC) billing account created synchronously
                    -> (Kafka) analytics records a registration
 2. Appointment booked -> appointment-service checks that the patient
    exists over gRPC (patient-service) and that the doctor exists over
    REST (auth-service internal) -> (Kafka) analytics
 3. Appointment completed -> (Kafka) billing auto-creates a consultation
    invoice -> (Kafka) INVOICE_CREATED -> analytics
 4. Invoice paid -> (Kafka) analytics revenue
 5. Patient deleted -> (Kafka) appointment-service cancels future
    appointments; billing closes the account
 6. Notifications (Kafka, all topics) -> notification-service emails the
    patient: welcome on PATIENT_CREATED, confirmation on
    APPOINTMENT_BOOKED or RESCHEDULED, notice on APPOINTMENT_CANCELLED,
    invoice on INVOICE_CREATED, receipt on INVOICE_PAID. Every email is
    logged in its DB and visible in Mailpit at http://localhost:8025.

B7. Code conventions
--------------------
 - Java 21 and Spring Boot 3.4.x (as today). Keep the package layout
   com.pm.<service>.{controller,service,repository,model,dto,mapper,
   exception,config,grpc,kafka}.
 - DTOs: use Java records for new DTOs.
 - Database schema: Flyway migrations in src/main/resources/db/migration
   (V1__init.sql, V2__seed.sql and so on). ddl-auto=validate.
 - Every new service gets: a Dockerfile (same pattern as the others), an
   Actuator health endpoint, springdoc, the standard error handler, an
   entry in docker-compose.yml and a route in the gateway.
 - Configuration comes from environment variables with sensible defaults
   in application.properties, so services still run outside Docker.

STEP 2: CROSS-CUTTING FOUNDATIONS
-----------------------------------------------------------------------------
 What
   - Standard error response (Part B4) in every service:
       * An ApiError record and a @RestControllerAdvice per service
         (servlet services) covering validation, not-found, conflict,
         ResponseStatusException and a catch-all 500 (log the stack trace,
         return a generic message).
       * api-gateway (reactive): 401 and 503 responses return the same JSON
         shape (custom ErrorWebExceptionHandler or a filter that writes
         the body).
   - Spring Boot Actuator in every service. Expose only health and info.
     Enable health groups for liveness and readiness.
   - docker-compose healthchecks:
       * Postgres: pg_isready.
       * Kafka: kafka-topics.sh --list against localhost:9092.
       * Services: curl or wget on /actuator/health. NOTE: the
         eclipse-temurin image may not include curl. Use a tiny Java-free
         approach (e.g. `wget -qO-` if available) or install curl in the
         Dockerfile runner stage.
       * depends_on with condition: service_healthy everywhere, so
         services start in the right order with no crash-retry noise.
   - Restart policy: restart: unless-stopped for app services.

 Why
   The frontend gets one predictable error format. The stack starts
   reliably. Health endpoints are an easy production-readiness point for
   interviews.
